Where the time goes on the board

The bit-exact check computes every reference frame with the Python golden model on the board's ARM. On the laptop one 640×480 reference takes 3.4 s; on the Cortex-A9 expect roughly ten times that, about 40 s (320×240: about 8 s). Six levels × frames × sizes adds up fast, so phase 6 uses few frames per image (the 2-lane image was already checked with 13 frames per level on 20 Oct). The FPGA itself and the timing runs take seconds. If the first 640×480 line takes much longer than a minute, drop 640×480 from the bit-exact runs and keep it for timing.

Without the attacker run, laptop B is only a second screen: it opens laptop A's dashboard and the wire stream, and the board's video goes straight to laptop A. In phase 11c laptop B sits in the middle: the board sends to B, B forwards to A, and B's attacks are started from A. The key exchange crosses B too; B relays it but cannot read it.

BoardA1 · A235 min

Single pipeline

VERSION 0x5EC00200: contract v2, levels E0–E4 only (no E5). That is expected.

Check the fabric column against the simulation

Each first_contact.md has columns load / DMA / ARM / fabric (ms). Fabric time is START to DONE counted by the FPGA itself. It should be close to the RTL cycle count:

ImageCycles per pixel (RTL)640×480 at 100 MHz640×480 at 125 MHz320×240 at 100 MHz
4 lanes0.5511.69 ms1.35 ms0.46 ms
2 lanes0.7932.44 ms— (built for 100)0.64 ms
single pipeline1.5194.67 ms— (built for 100)1.18 ms
How to read it
  • Fabric within ~10 % of the table: the encoder runs as simulated. This is the number the paper's A2 TODO waits for.
  • Fabric much larger and in_wait large: DDR does not deliver pixels fast enough (4 lanes need ~900 MB/s at 125 MHz). Report it; the YUYV image in phase 7 halves that traffic.
  • "Encode only" much larger than fabric: that is the ARM and Python around it, not the encoder. Report both columns.

Tamper inside the board: bits flipped after the tag

LaptopBoardA6 · hardware25 min

Phase 11 changes frames on the network. Here the change happens inside the camera: the tamper image flips one bit of one frame's scan between the encoder and the DMA, i.e. after the Ascon tag is computed. It stands for a fault or an implant anywhere on the path DMA → DDR → ARM → network card. It never touches a marker byte, so the frame still decodes as JPEG and only the tag can reveal the change. The claim to check: every shot costs exactly one rejected frame, and no other frame is rejected.

Control on the boardEffect
SW1 (up)enable. While SW1 is down, every bit passes unchanged.
SW0 (up)continuous: one bit flipped in every frame (for the live demo, not for the measurement)
BTN0, or a pulse on PMOD A pin 1one shot: one bit of the next frame
LED0 / LED1 / LED2 / LED3enabled / shot pending / continuous / toggles per tampered frame
BTN1 / BTN2 / BTN3protection level one down / one up (to E5) / back to automatic. Read by the ARM; the level changes at the next defence window (1 s) and shows on the dashboard.

Wire the Pico (optional, gives millisecond timing). 3.3 V only; connect no power pin. Pico on the receiver laptop's USB.

  • Pico GP15 (pin 20) → 1 kΩ → PMOD A pin 1 (JA1)
  • Pico GND (pin 18) → PMOD A pin 5 (GND)
  • Find its COM port in Device Manager → Ports. Install pyserial once: py -m pip install pyserial
Never

drive PMOD A from a 5 V board (Arduino Uno) without a level shifter. The FPGA pins are 3.3 V.

Set SW1 up, SW0 down. Then start the run on the receiver laptop. Replace COM5 with the Pico's port, or use --trigger manual and press BTN0 when the script says so (timing then only good to ~1 s).

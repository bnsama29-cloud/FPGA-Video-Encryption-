Before the board: build the board images from the final RTL

Vivado PC≈ 3.5 h, unattended

Run 11 measured the final RTL (commit d34604f) out of context: one, two and four lanes meet 150 MHz. The board images on your PC are still from runs 8, 9 and 10, i.e. older commits. Build all five from this commit so the board numbers and the paper's Vivado numbers describe the same design. After this the RTL is frozen.

Back up the current images, then pull.

Vivado PC · cmd
cd /d E:\FPGA-Video-Encryption-
git checkout hw-polish-arm-baseline
git pull
git log --oneline -1
xcopy /e /i /y future_work\board\overlay E:\backup_overlay_run10
Expect
  • git log shows 269284e or newer.
  • xcopy ends with "N File(s) copied". Paste this block one line at a time; pasting all at once fed the next lines into xcopy's questions last time (/y now answers them).

Build the five images. One line; the first part makes the single-pipeline and 2-lane images at 100 MHz, the second makes the 4-lane, 1080p and YUYV images (142.9 MHz first, falling back to 125 and then 100 MHz by itself) and packs the zip.

Vivado PC · cmd
py vivado\run_vivado_day.py --steps bd bd_lanes --fclk 100 --parallel 1 --jobs 2 & py vivado\run_vivado_day.py --steps bd_lanes4 bd_lanes4hd bd_lanes4yuyv parse --fclk 142 --parallel 1 --jobs 2
Expect
  • Each image ends with overlay meets timing at … MHz. A 142 MHz miss followed by a 125 MHz pass is a normal result, not a failure.
  • future_work\board\overlay\ then holds five pairs: secure_jpeg, secure_jpeg_lanes, secure_jpeg_lanes4, secure_jpeg_lanes4hd, secure_jpeg_lanes4yuyv, each .bit + .hwh.
  • vivado_results_<date>.zip: send it to Claude; its summary.txt starts with the commit and the SHA-256 of every bitstream.
Keep the PC awake

Plug it in, set sleep to "never", and do not click inside the window (a selection pauses the run until you press Esc). If you must stop: Ctrl+C, then end vivado.exe in Task Manager; ask Claude for the resume line.

Put the overlay folder in two safe places: the team drive and a USB stick. The board day must not depend on one PC.

A1 + A2: bit-exact on silicon, and the real speed

BoardA1 · A240 min

For each image: 10 frames per size and protection level are encoded on the FPGA and compared byte for byte (scan and tag) with the golden model; then 50 timed frames per size and level. --zero-copy lets the ARM write pixels straight into the DMA buffer.

4 lanes (the headline)

Board · ssh
python3 -m future_work.board.first_contact --bitfile future_work/board/overlay/secure_jpeg_lanes4.bit --sizes 320x240 640x480 --frames 10 --timing-frames 50 --zero-copy --out sim_out/board/lanes4_final
python3 -m future_work.board.first_contact --bitfile future_work/board/overlay/secure_jpeg_lanes4.bit --fclk 100 --sizes 320x240 640x480 --frames 10 --timing-frames 50 --zero-copy --out sim_out/board/lanes4_final_100

2 lanes and the single pipeline (for the lanes figure)

Board · ssh
python3 -m future_work.board.first_contact --bitfile future_work/board/overlay/secure_jpeg_lanes.bit --sizes 320x240 640x480 --frames 10 --timing-frames 50 --zero-copy --out sim_out/board/lanes2_final
python3 -m future_work.board.first_contact --bitfile future_work/board/overlay/secure_jpeg.bit --sizes 320x240 640x480 --frames 10 --timing-frames 50 --zero-copy --out sim_out/board/v2_final
Single pipeline

VERSION 0x5EC00200: contract v2, levels E0–E4 only (no E5). That is expected.

Check the fabric column against the simulation

Each first_contact.md has columns load / DMA / ARM / fabric (ms). Fabric time is START to DONE counted by the FPGA itself. It should be close to the RTL cycle count:

ImageCycles per pixel (RTL)640×480 at 100 MHz640×480 at 125 MHz320×240 at 100 MHz
4 lanes0.5511.69 ms1.35 ms0.46 ms
2 lanes0.7932.44 ms—0.64 ms
single pipeline1.5194.67 ms—1.18 ms
How to read it
  • Fabric within ~10 % of the table: the encoder runs as simulated. This is the number the paper's A2 TODO waits for.
  • Fabric much larger and in_wait large: DDR does not deliver pixels fast enough (4 lanes need ~900 MB/s at 125 MHz). Report it; the YUYV image in phase 7 halves that traffic.
  • "Encode only" much larger than fabric: that is the ARM and Python around it, not the encoder. Report both columns.

A5: the live link, with the board as the camera

LaptopBoardA530 min

The board encodes and encrypts, the laptop receives, verifies and shows the dashboard. Both ends first agree on a session key (ML-KEM-768 + X25519, authenticated by the pre-shared key), and the board pads frame sizes so they do not reveal motion.

Make a fresh pre-shared key on the laptop. It prints the key and both commands. The public key in configs/default.toml is never for a demo, and the key never goes through the dashboard, a web page or a chat: type it by hand on the board.

Laptop · cmd
py scripts\demo_key.py

Laptop first, then the board. Replace <KEY> with the printed key.

Laptop · cmd
py -m link.run_all --no-sender --pq-kex --set keys.master=<KEY> --set link.bind_host=0.0.0.0 --set link.sender_host=BOARD --set dashboard.bind_host=0.0.0.0
Board · ssh
python3 -m future_work.board.board_sender --bitfile future_work/board/overlay/secure_jpeg_lanes4.bit --pq-kex --set keys.master=<KEY> --set link.host=LAPTOP --set link.bind_host=0.0.0.0 --set link.pad=runmax --set sender.source=synthetic
Check
  • Both sides print kex: session key established … (ML-KEM-768 + X25519).
  • http://localhost:8000 on the laptop: "Sender started … board encoder", the receiver view playing, verified rising, rejected 0.
  • A second device opens http://LAPTOP:8000; VLC → Open Network Stream → http://LAPTOP:8000/stream/wire.mjpg shows the scrambled wire stream.
  • Press bit flip on the dashboard: one frame rejected, the policy jumps to E5, then back to E2. Film this with a phone.
Webcam

--set sender.source=webcam:0 with a USB camera on the board. Windows firewall: allow Python on private networks when asked.

When something goes wrong

look up the first error line
SymptomLikely cause and fix
only the red LEDSD card not written, or Boot jumper not on SD. Rewrite with Etcher, check the jumper.
ping failsWrong IP, laptop not in 192.168.2.x (direct cable), or the router isolates Wi-Fi clients. Read the IP on the serial console; try the direct cable.
ModuleNotFoundError: pynqMissing sudo -i and source /etc/profile.d/pynq_venv.sh.
RuntimeError: No Devices FoundRoot without a login shell. Use sudo -i, not sudo bash -c.
Overlay(...) fails, .hwh not foundThe .bit and .hwh are not side by side with the same base name.
fclk … is above the … MHz this bitstream was built for--fclk only lowers the clock. Drop it, or give a lower value.
VERSION register reads 0x…Wrong file or the IP has another name: python3 -c "from pynq import Overlay; print(Overlay('future_work/board/overlay/secure_jpeg_lanes4.bit').ip_dict.keys())", then pass --ip-name / --dma-name. Known values: 0x5EC00200 single pipeline, 0x5EC00382 2 lanes + E5, 0x5EC00384 4 lanes + E5, 0x5EC003C4 4 lanes YUYV + E5.
TimeoutError: DMA … not finished or STATUS.DONE never setTry --sizes 64x48 first. Old image (before 20 Oct): rebuild. Otherwise send Claude the first error and the command.
Mismatch at a small byte offsetHeader or registers (quantisation tables, session id, frame counter). Send the line to Claude.
Mismatch deep in the scanPixel order or a datapath fault. Rerun with --fclk 100; if that passes, it is the clock.
Passes, but fabric time far above the tableDDR starvation (in_wait large). Not a bug: report it; compare with the YUYV image.
Fails only with the new driverAdd --full-cache-ops and report it.
Dashboard empty, or every frame rejected (tag)Firewall, wrong IPs, laptop started after the board, or different keys on the two ends. Same keys.master on both; laptop first.
kex: no answer from the receiverThe laptop's run_all --pq-kex is not running or UDP 47006 is blocked. Allow it: netsh advfirewall firewall add rule name="secure-link" dir=in action=allow protocol=UDP localport=47000-47010
